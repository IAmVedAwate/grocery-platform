# Troubleshooting

This log grows with real incidents encountered during development — kept honest rather than speculative. Each entry: symptom, root cause, fix, and what would have caught it sooner.

## Format for New Entries

```
### <short symptom description>
**Encountered:** <date, phase>
**Symptom:** what was observed
**Root cause:** what was actually wrong
**Fix:** what resolved it
**Prevention:** what test/check/practice would catch this earlier next time
```

### ASP.NET Core Identity's defaults assume a single global tenant

**Encountered:** 2026-09-17, Phase 1 (auth + multi-tenant scaffolding)
**Symptom:** Registering a second store failed. First attempt: `500`, `DuplicateRoleName` — "Role name 'Admin' is already taken." After fixing that: a *different* `500`, a raw SQL exception — `Cannot insert duplicate key row in object 'dbo.AspNetRoles' with unique index 'RoleNameIndex'`. After fixing that too: a *third* `500` — `System.InvalidOperationException: Sequence contains more than one element` thrown from inside `UserStore.IsInRoleAsync` during `UserManager.AddToRoleAsync`.
**Root cause:** ASP.NET Core Identity was designed for a single-tenant app and assumes role names (and usernames) are unique **globally**, at three independent layers: (1) `RoleValidator<TRole>` checks `NormalizedName` uniqueness with no tenant awareness; (2) `IdentityDbContext`'s default model configuration puts a database-level unique index on `NormalizedName` (`RoleNameIndex`) and `NormalizedUserName` (`UserNameIndex`); (3) the default `UserStore.IsInRoleAsync` (called by `UserManager.AddToRoleAsync`) looks up the role by `NormalizedName` alone via `SingleOrDefaultAsync`, which throws once two stores both have an "Admin" role. Each fix surfaced the next layer — the validator, then the schema, then the store method itself.
**Fix:** Three coordinated changes, all in `Infrastructure/Identity/`: (1) `TenantScopedRoleValidator`/`TenantScopedUserValidator` replace the defaults, checking uniqueness scoped to `(StoreId, NormalizedName)` — registered via `services.RemoveAll<IRoleValidator<ApplicationRole>>()` before adding the replacement, since Identity's `AddRoles<TRole>()` registers its default additively, not with `TryAdd`. (2) `GroceryDbContext.OnModelCreating` explicitly overrides `RoleNameIndex`/`UserNameIndex` to non-unique and adds a `(StoreId, Normalized...)` composite unique index instead. (3) `IdentityServiceImpl.CreateUserAsync` inserts the `AspNetUserRoles` join row directly via the DbContext (`db.UserRoles.AddAsync(new IdentityUserRole<Guid> { UserId, RoleId })`) instead of calling `userManager.AddToRoleAsync(user, roleName)` — `RoleId` is genuinely globally unique, so this sidesteps the buggy name-based lookup entirely rather than trying to patch it.
**Prevention:** `TenantIsolationTests.TwoStoresCanEachHaveTheirOwnAdminRole_WithoutColliding` now asserts this directly — it's the regression guard. More generally: *any* library that manages its own entities (Identity, or a future third-party package) needs to be checked for global-uniqueness assumptions before being trusted in a multi-tenant system — the single-tenant-first design is the library's default, not something the docs advertise loudly.

### EF Core global query filter silently used a stale ITenantContext

**Encountered:** 2026-09-17, Phase 1 (Catalog module)
**Symptom:** Creating a product succeeded and correctly stored the right `StoreId`. But listing products for the *same* store that just created one returned an empty list — and this only showed up on the *second* store registered in the process; a single-store smoke test looked completely fine.
**Root cause:** The `Product` query filter was originally defined inside a separate `IEntityTypeConfiguration<Product>` class (`ProductConfiguration`) that took `ITenantContext` as its own constructor parameter: `HasQueryFilter(p => p.StoreId == tenantContext.StoreId)`. That lambda closes over *that configuration instance's* field — not over `GroceryDbContext`. EF Core only rebinds `this.<field>`-style member access **on the DbContext itself** per DbContext instance at query time; anything else captured in the filter's closure is evaluated once and baked into the compiled model, which EF Core caches for the app's lifetime (`OnModelCreating` runs exactly once). So the filter permanently used whichever `ITenantContext` existed at the moment the very first request built the model — every later request's *reads* silently filtered by the *first* request's tenant, while *writes* were unaffected (`ProductApplicationService` reads `ITenantContext` directly, per request, with no caching involved) — which is exactly why creation worked but listing didn't, and why it took a second tenant to notice.
**Fix:** Moved the `Product` query filter out of `ProductConfiguration` and into `GroceryDbContext.OnModelCreating` directly: `builder.Entity<Product>().HasQueryFilter(p => p.StoreId == tenantContext.StoreId)`, where `tenantContext` is `GroceryDbContext`'s own primary-constructor parameter (captured by the compiler into a private instance field on `GroceryDbContext` itself, so the filter genuinely is a `this.<field>` access). Category/Brand/Unit filters were already written this way and were never affected.
**Prevention:** `TenantIsolationTests.ProductCreatedByOneStore_IsInvisibleToAnotherStore_InListing` asserts both directions (store B sees nothing, store A still sees its own product) specifically because a filter that "always denies" or "leaks everything" are both plausible failure modes and need separate assertions. Rule going forward: a `HasQueryFilter` (or any per-request-scoped expression) must only ever reference the DbContext's *own* constructor-captured field, never a separately-instantiated configuration object's field.

### `WebApplicationFactory` config overrides are invisible to values read directly from `builder.Configuration` before `Build()`

**Encountered:** 2026-09-17, Phase 1 (Testcontainers-based integration tests)
**Symptom:** Every integration test hitting an authenticated endpoint (`/api/v1/products`) failed with `401` — `WWW-Authenticate: Bearer error="invalid_token", error_description="The signature key was not found"` — even though login itself succeeded and clearly returned a well-formed JWT. Confusingly, the tests were *also* connecting to a real database and returning correct data, which initially looked like proof the test's configuration override was working.
**Root cause:** `Program.cs` read `DB_CONNECTION_STRING`/`JWT_SIGNING_KEY`/etc. as local variables via `builder.Configuration["..."]` directly, between `WebApplication.CreateBuilder(args)` and `builder.Build()`. `WebApplicationFactory<TEntryPoint>`'s `ConfigureWebHost`/`ConfigureAppConfiguration` customizations for the **minimal hosting model** are applied as part of a deferred build-interception step around `Build()` itself — they are not visible to any code that reads `builder.Configuration` directly *before* that point. So `jwtSigningKey` silently captured the value from **local `dotnet user-secrets`** (a leftover dev secret from manual smoke testing), while `JwtTokenService` — which resolves `IConfiguration` via constructor injection, evaluated lazily *after* the host is fully built — correctly saw the test's override. Two different signing keys, one token: the "database worked" observation was a red herring — a manually-started SQL Server container was *still running* on the same port the connection string pointed at, from earlier manual `curl` testing, so the DB connection string had exactly the same eager-read bug but happened to still resolve to something that worked.
**Fix:** Converted every config value that a test might override to a **deferred, DI-resolved read**: `AddDbContext<GroceryDbContext>((sp, options) => ...)` (the `(IServiceProvider, DbContextOptionsBuilder)` overload) instead of a bare lambda closing over a pre-read connection string; `AddOptions<JwtBearerOptions>(...).Configure<IConfiguration>((options, configuration) => ...)` instead of `AddJwtBearer(options => ...)` with a captured local; same pattern for CORS via `AddOptions<CorsOptions>().Configure<IConfiguration>(...)`. All three now resolve `IConfiguration` from the DI container at the point they're actually needed, which is after `WebApplicationFactory` has finished applying its overrides.
**Prevention:** Found specifically because the diagnostic step was to `Console.WriteLine` the actual key value at both the token-issuing site and the token-validating site and compare them side by side, rather than continuing to reason abstractly about "should be the same." General rule adopted: **never read `builder.Configuration[...]` directly in top-level Program.cs code for a value that varies by environment** — always resolve it through DI (`Configure<IConfiguration>`, or a service constructor parameter) so both production startup and `WebApplicationFactory`-based tests observe the same, final, fully-merged configuration.
